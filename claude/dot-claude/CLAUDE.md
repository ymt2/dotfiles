## 抽象化のタイミング

* 事前の道具化は N=3 まで待つ。やり取りの形に依存する道具を単一事例で固めない
* N=1 で確定させると後発事例で寄せ直しになる。N=1 では「観察続行 + たたき台を残す」に留める
* 仮説と明確に枠付けるなら N=1 でも言語化してよい。禁じているのは早すぎる断定であって、早すぎる表現ではない
* 境界は二軸:「確信か仮説か」「道具か言語化か」

|      | 言語化   | 道具化       |
| ---- | -------- | ------------ |
| 仮説 | N=1 可   | たたき台まで |
| 確信 | N=3 待ち | N=3 待ち     |

### 実装時の振る舞い

* 1例目では共通化・抽象化・ヘルパー化をしない。素直な重複を許容する
* 抽象の候補に気づいたら、コードではなく応答側に「仮説」として明示する
* たたき台は捨てやすい形で置く。本採用の顔をさせない
* 3例目が揃った時点で初めて道具化を提案する

## テストコード

* 対象リポジトリに既存のテスト規約がある場合はそちらを優先する
* テストコードを書くときは Gherkin（ガーキン）記法を意識する（原典: https://cucumber.io/docs/gherkin/reference）
  * Gherkin は、特別なキーワードを用いて実行可能な仕様（executable specification）に構造と意味を与える記法。シナリオは仕様・ドキュメントであると同時にテストでもあり、全体としてシステムの実行可能な仕様となる
  * 主要キーワード（原典の定義に基づく）:
    * Feature — ソフトウェア機能の高レベルな説明を与え、関連するシナリオをグループ化する
    * Scenario（Example）— ビジネスルールを具体的に示す例。ステップのリストで構成される
    * Given — システムの初期コンテキスト（シナリオの場面設定）を記述し、システムを既知の状態に置く。ユースケースでいう事前条件
    * When — イベントまたはアクションを記述する。人による操作に限らず、他システムが引き起こすイベントも含む
    * Then — 期待される結果を記述する。実際の結果と期待する結果をアサーションで比較し、観測可能な出力を検証する
* テスト名は Given / When / Then が読み取れる形で書く（例: `test("Given 未ログインのユーザーが When 保護ページにアクセスすると Then ログインページにリダイレクトされる")`）
* テスト本体も Given（準備）→ When（実行）→ Then（検証）の順で構成する
